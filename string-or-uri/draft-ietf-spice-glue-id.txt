              GLobal Unique Enterprise (GLUE) Identifiers
                    draft-ietf-spice-glue-id-latest

Abstract

   This specification defines GLobal Unique Enterprise (GLUE)
   Identifiers, which are strings, some of which are also URIs, that
   identify businesses and organizations.  Every GLUE Identifier begins
   with a registered prefix that makes it globally unique.  The
   specification establishes an IANA registry of prefixes.  Registered
   prefixes can be the leading portion of identifiers from existing
   organizational identifier systems, such as "urn:lei:", or can be new
   simple string prefixes of the form "glue_name_".

1.  Introduction

   There are myriad entity identifier types for businesses and
   organizations.  With the increasing use of digital credentials, there
   is a need for a common methodology for expressing these identifiers
   such that claims about and by such entities can be made in a
   consistent and interoperable manner.

   This specification defines GLUE Identifiers.  A GLUE Identifier is a
   string that begins with a Prefix registered in an IANA registry
   established by this specification.  The Prefix makes the identifier
   globally unique.  Many existing organizational identifiers already
   have a globally unique form, for example as a URN or as an HTTPS URL.
   Such identifiers are used as they are, and the registry records the
   leading portion of the identifier as a Prefix, together with a
   reference to the specification that defines the identifiers.  This
   specification does not create new identifiers for these systems.  For
   identifier systems that have no such form, and for new systems, the
   registry also allows Prefixes of the simple form "glue_name_".

1.1.  Requirements Notation and Conventions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

1.2.  Terminology

   This specification uses the following terms:

   GLUE Identifier:  an identifier for an organization that is a string
      beginning with a registered Prefix.  It might also be a URI, URN,
      or IRI.

   Prefix:  the leading portion of a GLUE Identifier, registered in the
      registry established in Section 7.1.  Each GLUE Identifier begins
      with exactly one registered Prefix.  A Prefix typically
      corresponds to an External Authority.

   External Identifier:  the remainder of a GLUE Identifier after its
      Prefix.  It is allocated by the External Authority to identify a
      particular organization within the Prefix over which that
      authority has jurisdiction.

   External Authority:  an organization that allocates External
      Identifiers over which it has jurisdiction that are used in GLUE
      Identifiers with its Prefix(es).

2.  Core Concepts

   Every GLUE Identifier is a string consisting of the following
   components, in order:

   *  A registered Prefix

   *  The External Identifier

   This specification requires only that registered Prefixes are unique,
   and it relies on the IANA registry to enforce this property.  This
   specification does not address the equivalence or uniqueness of the
   full identifiers defined by the specification that is referenced from
   the registration of a Prefix.

2.1.  Uniqueness and Namespacing

   Each GLUE Identifier is a globally unique identifier.  An
   organization can be identified by multiple GLUE Identifiers, but each
   distinct GLUE Identifier can only refer to a single organization.  If
   multiple External Authorities have issued identifiers for the same
   organization (e.g., the organization has both a Dun & Bradstreet
   number and a Private Enterprise Number), then the same organization
   can be identified by GLUE Identifiers differentiated by the Prefix.
   Establishing whether multiple GLUE Identifiers refer to the same
   organization is out of scope for this specification.

   It is assumed that most registered organizational entity
   identification schemes already handle any namespacing necessary to
   achieve uniqueness as part of the External Identifier.  However, if
   collisions are possible within the set of possible external
   identifiers for an External Authority, then further namespacing is
   necessary at the Prefix level.  Such namespacing could be done by
   registering multiple Prefixes.  The combination of the Prefix and the
   External Identifier MUST result in a unique GLUE Identifier.

   For example, assume there is an External Authority FEA that provides
   identifiers for organizations in Singapore and South Korea.  The
   identifiers issued in Singapore are unique within Singapore, and the
   identifiers issued in South Korea are unique within South Korea, but
   there is no guarantee that an organization in Singapore will not be
   assigned the same identifier as an organization in South Korea.  Upon
   registration of FEA, it would be necessary to separately register two
   different Prefixes (e.g., glue_fea-sg_ and glue_fea-kr_) to provide
   differentiation between the two sets of External Identifiers.

2.2.  Lifecycle of Identifiers

   Organizations merge, split, are acquired, are renamed, and are
   dissolved or go bankrupt, and some identifier systems record
   relationships between organizations, such as parent and subsidiary.
   This specification does not define how identifiers behave through
   such events, and it does not define relationships or aliases between
   organizations.  Each External Authority handles these in its own way,
   and the resulting identifier behavior differs between systems.

   Specifications that register Prefixes SHOULD make the following clear
   to their readers, for the identifiers they reference:

   *  whether an External Identifier is permanent, or can change, for
      example when organizations merge or split;

   *  whether an External Identifier can ever be reused for a different
      organization, after its organization is dissolved or goes
      bankrupt, or for any other reason;

   *  how the status of an identifier is conveyed, such as an
      organization that is no longer active; and

   *  whether and how the External Authority expresses relationships
      between organizations, or alternative identifiers for one
      organization, if it does.

   Relying parties need this information to know whether a GLUE
   Identifier can be assumed to refer to the same organization over
   time.  An identifier that can be reassigned to a different
   organization weakens the global uniqueness that GLUE Identifiers are
   intended to provide.

3.  GLUE Identifiers

   A GLUE Identifier is a string that begins with a Prefix registered in
   the registry established in Section 7.1, followed by the External
   Identifier allocated by the External Authority.  A registered Prefix
   is either a Prefix for an existing identifier system, described in
   Section 3.1, or a new "glue_" Prefix, described in Section 3.2.

   No registered Prefix may be a leading substring of another registered
   Prefix, so that every GLUE Identifier begins with exactly one
   registered Prefix.  A Prefix is compared exactly as registered,
   except where its registration states that comparison is case-
   insensitive, as it is for the scheme and namespace of a URN.

3.1.  Prefixes for Existing Identifier Systems

   Many organizational identifiers already have a globally unique form,
   such as a URN or a URL.  The Prefix for such a system is the leading
   portion of the identifier, up to the point where the External
   Identifier allocated by the External Authority begins.  Examples are
   "urn:lei:" and "https://business-registry.example/companies/us_va/".
   The Prefix MUST contain enough of the identifier to be globally
   unique and to scope the External Identifiers that the External
   Authority allocates.  A URI scheme on its own, such as "https:", is
   not sufficient.

   For these systems the GLUE Identifier is the existing identifier,
   used as defined by the External Authority.  This specification does
   not define new identifiers for them, and it does not restrict the
   characters of their External Identifiers.  The specification
   referenced by the registration defines the syntax of the External
   Identifiers.

3.2.  New Prefixes

   Where an identifier system has no existing globally unique identifier
   form, a new Prefix of the form "glue_" name "_" can be registered.
   The name consists of a sequence of characters beginning with a letter
   or digit and followed by any combination of letters, digits, hyphen
   ("-"), or period (".").  This repertoire is compatible with DNS names
   [RFC1034].  The name MUST NOT contain an underscore, so the Prefix
   ends at the first underscore that follows "glue_".  Although names
   are case-insensitive, the canonical form is lowercase and documents
   that specify names must do so with lowercase letters.  An
   implementation should accept uppercase letters as equivalent to
   lowercase in names (e.g., allow "EXAMPLE" as well as "example") for
   the sake of robustness but should only produce lowercase names for
   consistency.  There is a limit of 253 characters for the length of a
   name.  The ABNF [RFC5234] for new Prefixes is:

   new-prefix = "glue_" name "_" name = (ALPHA / DIGIT) *252( ALPHA /
   DIGIT / "-" / "." )

   External Identifiers following a new Prefix consist of a sequence of
   unreserved characters Section 2.3 of [RFC3986]: letters, digits,
   hyphen ("-"), period ("."), underscore ("_"), and tilde ("~").  It is
   specific to the Prefix whether the External Identifiers are case-
   insensitive or case-sensitive.  When they are case-insensitive, the
   canonical form is lowercase and documents that specify External
   Identifiers MUST do so with lowercase letters.  Always using the
   canonical form of these identifiers means that code performing
   comparisons need not be aware of whether External Identifiers are
   case-sensitive or not; case-sensitive comparisons can always be
   performed on the whole GLUE Identifier.

   While the original representation of some External Identifiers may
   contain characters that are ignored, these MUST be omitted when used
   in GLUE Identifiers with a new Prefix.  For instance, Dun &
   Bradstreet [DUNS] identifiers sometimes contain hyphen characters
   that are ignored.  The DUNS numbers 12-345-6789 and 123456789 are
   considered to be equivalent.  The latter form without the ignored
   characters MUST be used as the External Identifier in GLUE
   Identifiers.

   Documents that define a new Prefix MUST NOT allow the representation
   of an External Identifier to contain characters outside the set
   above, such as the colon character.  Specifications MUST define a
   substitute character, such as period, that is used in place of any
   such character in External Identifiers.  Any substitution can be
   specified in the Transformation Rules in the IANA registration for
   the Prefix; see Section 7.1.

   GLUE Identifiers with a new Prefix are defined over the restricted
   US-ASCII syntax specified in this section.  Percent-encoding is not
   permitted.  Consequently, such GLUE Identifiers do not support
   representation of External Identifiers that use non-ASCII characters.
   New Prefixes are therefore limited to identifier systems whose
   representations can be expressed fully within the permitted character
   set.  This character set is a subset of the Unicode Assignables
   subset defined in [RFC9839].

   There is a limit of 1000 characters for an External Identifier
   following a new Prefix.  The ABNF [RFC5234] for such GLUE Identifiers
   is:

   glue-identifier = new-prefix external-identifier external-identifier
   = 1*1000( ALPHA / DIGIT / "-" / "." / "_" / "~" )

   For example, the following is a GLUE Identifier using the Prefix
   "glue_duns_" and the External Identifier "123456789".

   glue_duns_123456789

3.2.1.  Recommendations for New Prefixes

   The following recommendations apply to documents that register new
   Prefixes.

   *  Consider using a DNS name [RFC1034] under the control of the
      External Authority as the name (e.g., "business-
      registry.example"), because DNS names are already globally unique
      and have an established allocation and ownership model.  A DNS-
      name Prefix also helps limit conflicts between registrations.

   *  Consider using a UUID [RFC9562] in its lowercase hexadecimal
      string form as the External Identifier, because a UUID can be
      generated without coordination and is URL-safe.  For example,
      "glue_business-registry.example_3f2504e0-4f89-41d3-9a0c-
      0305e82c3301".

   *  Restrict both the name and the External Identifier to URL-safe
      characters, as defined by this section.

4.1.  Related Identifiers

   The specification that registers a Prefix can mention related
   identifiers, including URIs, URNs, IRIs and other strings.
   Establishing equivalence between those identifiers, or whether
   multiple identifiers refer to the same organization, is out of scope
   for this specification.  Implementations and relying parties MUST NOT
   assume equivalence between GLUE Identifiers and other identifiers
   unless such equivalence is explicitly defined by the specification
   referenced from the registration of the Prefix.

5.  Security Considerations

   The security considerations inherent to using URIs apply to GLUE
   Identifiers that are URIs.  Security considerations for URIs can be
   found in [RFC3986].

   The global uniqueness of GLUE Identifiers prevents situations in
   which the same identifier is allocated in different local namespaces
   and cannot be disambiguated when used.  For instance both Canadian
   and Singaporean organization registries might use the local
   identifier "42", but with these referring to different organizations.
   Embedding these local identifiers in GLUE Identifiers with distinct
   Prefixes enables disambiguation.

   A Prefix identifies the namespace, not the party presenting an
   identifier.  A GLUE Identifier on its own does not authenticate that
   the presenter is the organization it names.  Relying parties need to
   establish that by other means.

   A DNS name used in a Prefix can change hands when the domain
   registration lapses or is transferred.  Registrations of such
   Prefixes are subject to the review described in Section 7.1.
   Registered Prefixes remain bound to the registrant of record in the
   registry, whatever later happens to the domain.

6.  Privacy Considerations

6.1.  Private Identifiers as Corporate Identifiers

   There are some corporate identifiers that make use of personal
   identifiers.  For example, this is the case for some registered sole-
   proprietor businesses in the United States, where the Tax ID may be
   the same as the Social Security Number (SSN) of the business owner.
   Where the Tax ID uniquely identifies the business, the SSN uniquely
   identifies an individual.

   It is possible for such business identifiers to be represented as
   GLUE Identifiers.  An identifier's expression as a GLUE Identifier
   does not change the privacy characteristics of that identifier.  The
   same cautions and concerns need to be taken with the GLUE Identifier
   representation as with the original identifier.

   Implementers storing or evaluating GLUE Identifiers are encouraged to
   be aware the privacy characteristics of each identification scheme
   represented by a Prefix and to appropriately handle any GLUE
   Identifier that violates privacy policies.

7.  IANA Considerations

7.1.  GLUE Prefix Registry

   This specification establishes the IANA "GLUE Prefix" registry of
   Prefixes for GLobal Unique Enterprise (GLUE) Identifiers.

   Each entry registers a Prefix for use in GLUE Identifiers.  The
   organization responsible for the Prefix is recorded.  A registered
   Prefix is either the leading portion of an identifier in an existing
   organizational identifier system (such as "urn:lei:"), or a new
   Prefix of the form "glue_name_" as defined in Section 3.2.

   IANA is requested to create the "GLobal Unique Enterprise (GLUE)
   Identifiers" registry group located at
   https://www.iana.org/assignments/glue-identifiers/ and place this
   registry there.

   Values are registered on a Specification Required (Section 4.6 of
   [RFC8126]) basis after a two-week review period on the spice-ext-
   review@ietf.org mailing list, on the advice of one or more Designated
   Experts.  However, to allow for the allocation of values prior to
   publication of the final version of a specification, the Designated
   Experts may approve registration once they are satisfied that the
   specification will be completed and published.  However, if the
   specification is not completed and published in a timely manner, as
   determined by the Designated Experts, the Designated Experts may
   request that IANA withdraw the registration.

   Registration requests sent to the mailing list for review should use
   an appropriate subject (e.g., "Request to register GLUE Prefix
   example").

   Within the review period, the Designated Experts will either approve
   or deny the registration request, communicating this decision to the
   review list and IANA.  The Designated Experts verify that a
   specification exists and that the proposed Prefix is unique, is not a
   leading substring of a registered Prefix, and does not have a
   registered Prefix as a leading substring.  A new Prefix also has to
   conform to the syntax in Section 3.2.  Experts are encouraged to be
   biased towards approving registrations unless they are abusive,
   frivolous, or actively harmful (not merely aesthetically displeasing
   or architecturally dubious).

   Denials should include an explanation and, if applicable, suggestions
   as to how to make the request successful.  If the designated experts
   are not responsive, the registration requesters should contact IANA
   to escalate the process.

   Criteria that should be applied by the Designated Experts includes
   determining whether the proposed registration duplicates existing
   functionality, determining whether it is likely to be of general
   applicability or whether it is useful only for a single application,
   and whether the Prefix is distinct enough to avoid confusion with an
   existing registration.  For a Prefix for an existing identifier
   system, the Designated Experts check that the registration references
   the specification of those identifiers, operated by an External
   Authority, and that the Prefix contains enough of the identifier to
   be globally unique, as described in Section 3.1.  Equivalent forms of
   an identifier system that already have a registered Prefix should not
   be registered under a new Prefix; the existing identifiers are used
   instead.  Where a Prefix contains a DNS name, the Designated Experts
   should check that the requester controls that DNS name.  For a new
   Prefix that is not tied to an existing identifier system, the
   specification needs to describe how External Identifiers are
   allocated and how their uniqueness within the Prefix is ensured.  The
   Designated Experts should also check that the specification addresses
   the topics in Section 2.2.  The recommendations in Section 3.2.1
   apply.

   IANA must only accept registry updates from the Designated Experts
   and should direct all requests for registration to the review mailing
   list.

   It is suggested that multiple Designated Experts be appointed who are
   able to represent the perspectives of different applications using
   this specification, in order to enable broadly-informed review of
   registration decisions.  In cases where a registration decision could
   be perceived as creating a conflict of interest for a particular
   Expert, that Expert should defer to the judgment of the other
   Experts.

   The reason for the use of the mailing list is to enable public review
   of registration requests, enabling both Designated Experts and other
   interested parties to provide feedback on proposed registrations.
   The reason to allow the Designated Experts to allocate values prior
   to publication as a final specification is to enable giving authors
   of specifications proposing registrations the benefit of review by
   the Designated Experts before the specification is completely done,
   so that if problems are identified, the authors can iterate and fix
   them before publication of the final specification.

7.1.1.  Registration Template

   Prefix:  The Prefix to be registered.  For a Prefix for an existing
      identifier system, it is the leading portion of the identifier, as
      described in Section 3.1.  For a new Prefix, it MUST conform to
      the "new-prefix" syntax in Section 3.2 and any letters MUST be
      expressed in lowercase characters.  The registration states
      whether comparison of the Prefix is case-insensitive.

   Example:  An example GLUE Identifier using the Prefix.

   Organization:  The organization responsible for the Prefix.

   Transformation Rules:  Syntactic transformations applied to the
      original External Identifiers when creating the GLUE Identifier,
      or "N/A" if none.

   Change Controller:  For IETF stream RFCs, use "IETF".  For others,
      give the name of the responsible party.  Other details (e.g.,
      postal address, e-mail address, or home page URL) may also be
      included.

   Specification Document(s):  Reference to the document or documents
      that specify the identifiers for the Prefix to be registered,
      preferably including URLs that can be used to retrieve the
      documents.  An indication of the relevant sections may also be
      included, but is not required.

Document History

   -11

   *  Defined GLUE Identifiers as strings that begin with a registered
      Prefix, which makes them globally unique.

   *  Prefixes for existing identifier systems are the leading portion
      of the existing identifier, such as "urn:lei:", and no new
      identifiers are defined for them.

   *  Added new Prefixes of the form "glue_name_" for identifier systems
      without an existing globally unique form.

   *  Removed the "glue:" URI scheme and its registration.

   *  Renamed "Authority Identifier" to "Prefix".

   *  Added recommendations for new Prefixes: DNS names, UUIDs, and URL-
      safe characters.

   *  Registered the Wikidata entity URI prefix as an example of a
      general-purpose identifier.

   *  Encouraged specifications that register Prefixes to state how
      identifiers behave through mergers, dissolution, reuse, and
      relationships between organizations.

   *  Stated that equivalence between identifiers, and establishing
      whether multiple identifiers refer to the same organization, are
      out of scope.

   *  Replaced the example LEI, and corrected "20-digit" to
      "20-character".

   *  Updated the D-U-N-S reference.

   -10

   *  Removed GS1 usage.

   -09

   *  Changed from using a URN namespace to a URI scheme, based on
      feedback from the URN designated experts.

   -08

   *  Addressed urn:glue registration feedback by Dale Worley about
      identifier uniqueness and defining Transformation Rules, when
      needed.

   *  Addressed urn:glue registration feedback by Peter Saint-Andre
      about using "URN" rather than "URI", applying suggested language
      about when multiple External Authorities have issued identifiers
      for the same organization, and correcting issues with the registry
      descriptions.

   -07

   *  Registered urn:glue per Amanda Baber's instructions.
